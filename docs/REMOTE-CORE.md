# 远程 core 模式（Windows UI + 服务器运行时）——设计与影响分析

> 状态：已实现，待打包验证。上游：`flyhero/antumi` 0.21.8（外部治理仓库，本改动是本机分支，
> 不向上游提 PR）。0.21.8 合入后，远程成为上游「后端位置」（本机 / WSL / 远程）的第三个
> 选项：选择在 设置 → 后端位置 里做出并写入 `backend.json`，`remote.json` 只保存连接配置；
> 远程连不上时**不回退本机**，而是明确显示原因——这与 WSL 的回退语义不同，见 §5。

## 1. 目标与领域现状

目标：桌面端在 **Windows 本机**原生运行；**任务、git、worktree、agent 进程、持久化全部留在
开发服务器**上。用户要的是「本地窗口的体验 + 服务器算力」。

### 领域内的既有方案

| 方案 | 代表 | 本项目的取舍 |
| --- | --- | --- |
| **SSH 端口转发 + 远程服务** | VS Code Remote-SSH、JetBrains Gateway、X11 forwarding | **采用。** 与 Antumi「core 是纯 Node 服务、只绑回环」的既有设计最贴合；不新增暴露面，复用用户已有的 SSH 身份 |
| 暴露 core 端口 + TLS + token | 自建 API 网关 | 否决。把「能以 bypass 起 agent」的控制面直接放公网，认证只有 bearer token；与既有 `flexible` 模式的明文回源叠加会更糟 |
| 反向隧道（cloudflared/ngrok） | §7.34 的既有做法 | 否决为主路径。多一跳第三方、且这条链路的价值等于整台机器；作为**备选**保留（见 §6） |
| 远程桌面/VDC（noVNC、RDP） | 本次会话早先的实现 | 否决。已实测可行，但操作系统级投递的体验差、带宽重、且把所有窗口暴露给同一通道 |
| 客户端重写为 Web UI | — | 否决。等于重写整个渲染层，且丢掉 Electron 的内置浏览器/终端 |

**选 SSH 的核心理由**：Antumi 已经把「界面」和「执行」分在两个进程里（`docs/ARCHITECTURE.md`：
core 持有任务/git/worktree/agent，desktop 只是客户端）。远程模式不是加功能，是把这条**已经
存在的边界**从「同机回环」延伸到「经隧道」——改动面因此可控。

## 2. 三处硬编码（实测确认的代码事实）

| # | 位置 | 现状 | 为何是障碍 |
| --- | --- | --- | --- |
| 1 | `packages/core/src/rpc-server.ts:135` | `host: '127.0.0.1'` 写死 | 监听地址不可配。**但这不是要改的那一处**——见 §3 的决定 |
| 2 | `packages/protocol/src/rpc.ts:1125` | `coreUrl()` 返回 `ws://127.0.0.1:<port>` | 远程端点的地址无法表达 |
| 3 | `packages/desktop/src/main/backend.ts` `runningCore()` | 用 `127.0.0.1:<port>` 的可达性判断「本地 core 已在跑」 | **最隐蔽**：远程模式下它会判定「没有 core」，于是无条件拉起一个**本地** core，把远程配置静默覆盖成两个 core 并存 |

第 3 条是这次改动最重要的发现：它不是「连不上」，而是「连上了但同时又起了一个本地实例」，
表现为数据分叉、任务出现在错误的一侧，且没有任何报错。

## 3. 决定：不改 core 的绑定地址

「让 core 监听 0.0.0.0 再由隧道转发」是这类需求最常见的实现，这里**不采用**：

- `rpc-server.ts:133` 的注释自己写明「any page can open `ws://127.0.0.1`, so the port alone
  is not a boundary」——它依赖的是**回环**这个边界，token 是第二层而不是第一层。
- 一旦绑非回环，任何能路由到该端口的东西（同网段、容器、隧道配错）都直接面对一个
  **能以 bypass 起 agent** 的控制面。这等于把 §7.36 里已经讨论过的赌注重新引入一次，
  而且这次是长期的、默认开启的。
- SSH 本地转发（`ssh -L`）在**客户端**建立 `127.0.0.1:<本地端口>` → 服务器回环的映射，
  服务器端**不需要**监听任何非回环地址。边界保持不动。

代价：必须有一个 SSH 连接常驻。这与 VS Code Remote 的取舍相同，是本方案唯一的强依赖。

## 4. 实现

### 4.1 配置与发现

- `~/.antumi/remote.json`（600，可选）：
  ```json
  { "sshHost": "dev-us", "corePort": 12150, "remoteHome": "/home/claude/.antumi" }
  ```
  存在使「远程主机」出现在 设置 → 后端位置 的可选项里；**选择**（写入 `backend.json` 的
  `{kind:'remote'}`）才进入远程模式。文件不存在 = 与上游行为**完全一致**（零影响）；文件
  损坏时该选项以禁用态展示原因，不会悄悄退回本地。
- 远程模式启动时建立 `ssh -N -L 127.0.0.1:<corePort>:127.0.0.1:<corePort> <sshHost>`，
  并写入 `~/.antumi/core.json`（与本地模式同一个文件，因此渲染层与 MCP 客户端**无需任何改动**）。
- `coreUrl()` 不变：它拼的仍是 `127.0.0.1:<port>`，而该端口现在是隧道本地端。**这是刻意的**
  ——把「端点在哪里」的复杂度收敛在隧道一处，不扩散到协议层。

### 4.2 远程 core 的生命周期

远程会话是 `AppBackend` 三种后端位置之一：`RemoteSession.start()` 跑 `ssh <host>
'antumi-core-start'`（幂等；已有 core 则复用，读回它的 `core.json` 拿到端口）并建隧道。
`AppBackend` 在选择远程时**不执行** `ensureBackend()`，隧道建不起来就只有一个待展示的
problem（设置页与「等待 core」横幅都读它），本机端什么也不起——静默地服务本机 core 正是
这个模式要防的事故。停止/安装流程只断开隧道这个本机子进程——远程 core 的生命周期
**属于服务器**，不属于这个窗口。

### 4.3 内置浏览器

core 通过 `browser/host.json` 找浏览器宿主，而宿主是**桌面端**进程。远程模式下该文件在
服务器侧，桌面端无法写。处理：远程模式下由桌面端把 host 端点通过一个 RPC 告知 core，
而不是走文件交接。**若这一步不做，agent 的浏览器工具会指向不存在的一端**——这是最容易
被漏掉的二阶影响，因为它只在 agent 主动开浏览器时才暴露。

### 4.4 文件预览

`antumi-preview://` 由桌面端主进程 `readFile`。远程模式下文件在服务器上。改为经 `files.read`
RPC 取内容（该 RPC 已存在且返回文本）。**代价**：二进制预览（图片）需要新的 RPC；
本版先覆盖文本类，图片走「不可用」分支并在界面说明。

## 5. 二阶 / 三阶影响

| 影响 | 方向 | 处理 |
| --- | --- | --- |
| **两个 core 并存**（§2 #3） | 数据分叉、静默覆盖 | 远程是显式选择而非「文件存在即生效」；`AppBackend` 在选择远程时跳过 `ensureBackend()`，失败时也不回退本机 |
| 自动更新 | 打包版会替换 App 自身，但**不**该重启远程 core | `stopForInstall()` 在远程下只停掉隧道这个本机子进程，远端不动 |
| 多窗口/多标签 | 每个窗口都建 SSH 隧道会打架 | 隧道单例，绑定到 app 生命周期，不是窗口 |
| SSH 断线 | UI 显示「等待 core」，与本地 core 重启的表现一致 | 复用既有 `waiting-for-core` 状态；不新增 UI 概念 |
| 端口冲突 | 本地 `corePort` 被占 | 用固定的高位端口（12150，端口册已登记），启动前探测并给出明确报错 |
| token | 远程 core 的 token 经 SSH 回传，不落公网 | `core.json` 仍是 600；隧道是加密的 |
| **agent 的 PATH/cwd** | daemon 在服务器上跑，agent 看到的是服务器的文件系统——**这正是想要的** | 无改动；但要写清楚：远程模式下「打开项目」是服务器的路径 |
| 版本错配 | 本机 App 新版 + 服务器 core 旧版 | core 已有 `protocolVersion`；启动时比对，不一致就在界面明说，而不是静默失败 |
| 长期维护 | 与上游分歧变大 | 远程挂在上游自己的 `AppBackend` 会话形状上（`remote-core.ts` 的 `RemoteSession` + 共享 schema 里一个 `{kind:'remote'}` 分支），不动 core 的绑定、不动协议层；上游升级时冲突面可控 |
| 用户行为 | 「本地项目」不再能选 | 设置界面要明确说明当前是远程模式、项目路径属于服务器 |

**三阶影响（更远）**：
- 若将来要支持**多个**远程主机，`remote.json` 会变成列表，隧道单例会变成池。当前先不做
  ——一个 `sshHost` 覆盖真实需求，加列表需要连接管理 UI，属于 YAGNI。
- 手机端网关（core 的 7820）在远程模式下仍在服务器上；手机连服务器即可，不受本改动影响。
- 若将来上游自己实现了远程 core，这里的改动应当被删除而不是合并——所以实现上尽量贴着
  「最小侵入 + 可整体移除」的形状。

## 6. 未采纳但记录在案的备选

**反向隧道**（cloudflared 指向本机）：优点是不需要用户有 SSH 客户端；缺点是引入第三方
在链路上、且需要额外的认证设计。若某天要在没有 SSH 的设备（如公司的受管机）上用，再考虑。

## 8. 已知缺口（明确不做，不是遗漏）

- **内置浏览器在远程模式下被禁用**（`index.ts` 里按 remote 判断跳过 `startBrowserHost`）。
  agent 的浏览器工具会等待一个不可达的宿主。补齐需要一个把 host 端点告知远端 core 的通道，
  见 §4.3。**这是"明确地少一个功能"，不是"静默地坏一半"**——后者更难排查。
- **聊天里的图片预览**在远程模式下不可用（走 `files.read`，只回文本）。文本/HTML/SVG 正常。
- 远程 core 的**生命周期属于服务器**：App 退出不停它，安装更新也不停它。`ops/remote-core.sh`
  是幂等的启动入口。
